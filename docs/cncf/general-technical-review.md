## Day 0 - Planning Phase

### Scope

Draft written from the repository and the documentation; to be reviewed by a contributor.

**Vision and goals.** FerrisKey is an open source Identity and Access Management system written in Rust, built for teams who want an IAM they can read, deploy and operate without the weight of the older platforms ([What is FerrisKey](https://github.com/ferriskey/website/blob/2529ade8da32ac17b70c0c2e7e98f47de17b5fd1/apps/docs/src/content/docs/discover/default/en/what-is-ferriskey.mdx)). The goals stated in [GOVERNANCE.md](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/GOVERNANCE.md): identity and access management, OAuth 2.0 and OpenID Connect, multi-tenant realms, policy and role enforcement. Design goals: performance and low memory through Rust and async I/O, a hexagonal architecture that keeps the domain testable, modules that can be enabled independently, secure defaults, and cloud native packaging (container images, Helm charts, an operator).

**Use cases.** Primary: single sign-on and token issuance for an organization's applications and services over OpenID Connect and OAuth 2.0 (authorization code with PKCE, client credentials, device flow, token exchange, refresh token rotation, back-channel logout); multi-tenant hosting where each realm isolates users, clients, roles, credentials and settings. Additional: customer and B2B identity with organizations, groups, membership and attributes, a themable hosted login portal and account self-service; multi-factor authentication with TOTP, WebAuthn passkeys, magic links and recovery codes; identity brokering to Google, GitHub, Discord and any OpenID Connect provider; FerrisKey as a SAML 2.0 identity provider; audit events (SeaWatch) and webhooks; migration from Keycloak, Zitadel or Supabase through the CLI import, including password hashes. Out of scope today: acting as an LDAP or Active Directory server, storing arbitrary secrets, and exporting password hashes (refused on purpose, see [Export and Import](https://github.com/ferriskey/website/blob/2529ade8da32ac17b70c0c2e7e98f47de17b5fd1/apps/docs/src/content/docs/discover/default/en/guides/portability.mdx)). [to confirm]

**Roadmap process.** The public roadmap is at https://ferriskey.rs/roadmap with three columns: current capabilities, next, explorations. [ROADMAP.md](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/ROADMAP.md) is the entry point from the repository and lists the epics in progress; every started item is an issue labelled `epic` and attached to a milestone (v0.10 at the time of writing). Maintainers review the roadmap at each minor release. Items are proposed through GitHub Discussions following the RFC process in GOVERNANCE.md; decisions use lazy consensus with a 72 hour window and a maintainer vote when needed. The maintainer ladder is in GOVERNANCE.md and [MAINTAINERS.md](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/MAINTAINERS.md): contributors become maintainers on consistent contributions and the approval of two existing maintainers; there are five maintainers from four affiliations, and affiliations must be updated within 30 days.

**Target personas.** Platform and operations engineers who deploy and run the service (Helm, operator, Compose); application developers who integrate OpenID Connect, OAuth 2.0 or SAML clients; realm administrators who manage users, clients, roles and policies in the console; end users who sign in through the portal and manage their account.

**Target organizations.** Any software team or vendor that needs authentication for one or many applications, including multi-tenant SaaS; cloud and hosting providers who run identity as part of their platform; organizations in regulated or sovereignty-sensitive sectors who need to self-host identity on their own infrastructure; consultancies who build on it. Current adopters in [ADOPTERS.md](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/ADOPTERS.md): a French open source cloud provider (production), a healthcare infrastructure company, an AI SaaS (production) and an engineering consultancy.

**End user research.** No formal study has been published. Signals used so far: the adopters list, GitHub Discussions and issues from evaluating teams (for example [#1186](https://github.com/ferriskey/ferriskey/issues/1186)), and the migration imports requested by users coming from other IAMs.

### Usability

Draft written from the repository and the documentation; to be reviewed by a contributor.

**How personas interact with the project.** Operators install with one `helm install` from an OCI registry, or with the `FerrisKeyCluster` custom resource through the operator, or with Docker Compose profiles. Administrators use the web console (React) scoped by realm, or the REST API documented with OpenAPI, or the [CLI](https://github.com/ferriskey/ferriskey-cli) (realms, clients, users, contexts, imports from Keycloak, Zitadel and Supabase), or the [Terraform provider](https://github.com/ferriskey/terraform-provider-ferriskey). Developers point their application at the realm's discovery document and use any standard OpenID Connect, OAuth 2.0 or SAML 2.0 library. End users sign in on the hosted portal and manage credentials, sessions, MFA and profile in the account pages.

**UX and UI.** The console groups features by module (realms, users, clients, roles, organizations, Trident for MFA, Abyss for federation, SeaWatch for security events, webhooks, portal themes and layouts, email templates). The login portal is themable per realm with a layout builder; themes, layouts and email templates export and import as JSON so a brand is built once and shipped to every realm. The console and the public pages are localized (English and Chinese, with a CI check on locale parity).

**Integration in production.** Standards first: every relying party that speaks OpenID Connect, OAuth 2.0 or SAML 2.0 works without a FerrisKey specific library; the console itself is a public OpenID Connect client. Observability: Prometheus metrics on `/metrics` with a `ServiceMonitor` option in the chart, OpenTelemetry tracing over OTLP, structured JSON logs, a ready made [SigNoz dashboard](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/docs/ferriskey-signoz-dashboard.json). Outbound integrations: webhooks on lifecycle events, SMTP for email, upstream identity providers, client metadata documents. Deployment: Ingress or Gateway API HTTPRoute rendered by the chart, cert-manager annotations in the documented example, an ArgoCD installation guide, and a migration Job that applies schema changes on each deploy.

### Design

Draft written from the repository and the documentation; to be reviewed by a contributor.

**Design principles.** Hexagonal architecture: the domain knows nothing about HTTP, SQL or SMTP; ports are traits, adapters implement them, and `ApplicationService` is the single place where the object graph is assembled ([Architecture](https://github.com/ferriskey/website/blob/2529ade8da32ac17b70c0c2e7e98f47de17b5fd1/apps/docs/src/content/docs/discover/default/en/guides/architecture.mdx)). Modules own one part of identity management and move to their own crate under `libs/` when they are worth versioning separately. Type driven invariants and no `unwrap` in production code. Behaviour is specified by integration tests at the HTTP boundary, run against PostgreSQL in CI. Secure by default, with explicit toggles to loosen (see Security).

**Architecture requirements by environment.** Proof of concept: one container with the standalone Compose profile, or the chart with its embedded PostgreSQL. Development: Compose profiles building from source, `cargo run` with a local PostgreSQL. Test: CI runs unit, doc and integration tests against PostgreSQL 18 with every ignored test included. Production: an external PostgreSQL with TLS, several API and console replicas, TLS at the Ingress or Gateway, secrets from an external manager, metrics and audit forwarding ([Production Guide](https://github.com/ferriskey/website/blob/2529ade8da32ac17b70c0c2e7e98f47de17b5fd1/apps/docs/src/content/docs/kubernetes/default/en/production-guide.mdx)).

**Service dependencies in the cluster.** PostgreSQL is the only required dependency. Optional: an SMTP relay for email, outbound HTTPS to upstream identity providers, client metadata documents and webhook endpoints, an Ingress controller or Gateway API implementation, cert-manager, Prometheus for the `ServiceMonitor`. No cache, queue or object store.

**Identity and Access Management.** FerrisKey is itself the IAM. Every user, client, role, credential and setting belongs to a realm. Roles are bitmasks mapped to users and clients; client scopes and protocol mappers decide what enters a token; organizations add B2B tenancy inside a realm. The admin API is authorized by realm roles and policies, with a Cedar based authorization crate ([libs/ferriskey-authz-cedar](https://github.com/ferriskey/ferriskey/tree/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/libs/ferriskey-authz-cedar)) being introduced. Protocols: OpenID Connect and OAuth 2.0 (authorization code with PKCE, client credentials, resource owner password per client, device flow, token exchange, refresh rotation, revocation, introspection, back-channel logout, dynamic client registration), SAML 2.0 as identity provider, brokering to upstream providers. Required actions (password update, OTP or passkey setup, email verification) gate a login until completed.

**Sovereignty.** Self-hosted by design: the service runs entirely on the adopter's infrastructure and the only data store is the adopter's PostgreSQL. No outbound call is required to operate; every outbound destination (identity providers, SMTP, webhooks, client metadata) is configured by the adopter and refused by default when it points at a private address. Portability: realm content (themes, layouts, templates) exports as JSON, and users can be imported from other IAMs with their password hashes. A French sovereign cloud provider runs FerrisKey in production.

**Compliance.** No certification is claimed. Features that support compliance work: SeaWatch security events with a per-realm PII mode and pseudonymisation key, exportable audit trails, account lockout and password policies, session management with revocation. GDPR compliance and user self-service are an epic in progress ([#992](https://github.com/ferriskey/ferriskey/issues/992)).

**High availability.** The API and the console are stateless; all state, including sessions and tokens, is in PostgreSQL, so replicas scale horizontally without sticky sessions (the documented production values use three API and two console replicas). Rolling updates are the default strategy and the migration Job runs before pods roll. Database high availability is the adopter's choice (managed service or an operator such as CloudNativePG). Gap: the chart has no PodDisruptionBudget template yet; the production guide lists applying one as an adopter task.

**Resource requirements.** Chart defaults: API 128 MiB requested and 512 MiB limit, console 32 to 64 MiB, migration Job 128 to 512 MiB, embedded PostgreSQL 128 to 256 MiB; no CPU values are set by default. Measured on a single API process while creating 1,000 realms: resident memory between 37 and 69 MiB ([#1610](https://github.com/ferriskey/ferriskey/issues/1610)). Network: the API listens on 3333 and the console on 80 inside the cluster; outbound to PostgreSQL and to the optional destinations above. Reproducible benchmarks against Keycloak are tracked in [#1621](https://github.com/ferriskey/ferriskey/issues/1621).

**Storage requirements.** The API and console containers run on a read-only root filesystem with a 100 MiB `emptyDir` on `/tmp`. Persistent storage is PostgreSQL only; the embedded PostgreSQL in the chart uses a PersistentVolumeClaim and is meant for trials.

**API design.** REST over JSON. Realm-scoped resources live under `/realms/{realm_name}/...` (users, clients, roles, organizations, webhooks, email templates, portal); the protocol endpoints under `/realms/{realm_name}/protocol/openid-connect/...` and discovery at `/.well-known/openid-configuration` and `/.well-known/oauth-authorization-server`. The OpenAPI document is generated from the handlers (`utoipa`) and served at `/api-docs/openapi.json` with Swagger UI, ReDoc, RapiDoc and Scalar; the console's TypeScript client, the CLI and the Terraform provider are built from it. Defaults are described under Security; the configuration beyond defaults for a real deployment is the public host, allowed origins, TLS or a proxy, an admin password from a secret and SMTP ([Configuration](https://github.com/ferriskey/website/blob/2529ade8da32ac17b70c0c2e7e98f47de17b5fd1/apps/docs/src/content/docs/discover/default/en/guides/configuration.mdx)). New API types: one namespaced CustomResourceDefinition, `ferriskeyclusters.ferriskey.rs` at `ferriskey.rs/v1alpha1`, reconciled by the operator through the Kubernetes API with `kube-rs`; it creates Deployments, Services, Secrets and a migration Job and reports status and phase. Versioning: the project is pre-1.0 and follows semantic versioning with release candidates; schema changes ship as SQL migrations with down migrations and run through the migration Job or the `migrate` command; the CRD is at `v1alpha1`. Gap: there is no written deprecation policy for the HTTP API or the CRD yet; breaking changes are called out in the release notes.

**Release process.** Releases are tags `vX.Y.Z`, preceded by `-rcN` candidates. A tag triggers the GitHub release with generated notes ([release.yaml](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/.github/workflows/release.yaml)), multi-architecture images for the API, operator and console pushed to `ghcr.io/ferriskey` with semver, major.minor, major and sha tags ([docker.yaml](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/.github/workflows/docker.yaml)), and the two Helm charts pushed to `oci://ghcr.io/ferriskey/charts` at the same version ([helm.yaml](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/.github/workflows/helm.yaml)). Cadence over the last months: 0.7.0 (2026-06-30), 0.7.1 and 0.7.2 as patch releases, 0.8.0 (2026-09-15), 0.9.0 (2026-10-03). Minor releases carry features and may carry breaking changes while pre-1.0; patch releases carry fixes; security fixes land in the latest minor (SECURITY.md).

### Installation

Draft written from the repository and the documentation; to be reviewed by a contributor.

**Installation and initialization.** Kubernetes: `helm install ferriskey oci://ghcr.io/ferriskey/charts/ferriskey --namespace ferriskey --create-namespace` brings up the API, the console, a migration Job and an embedded PostgreSQL, and generates the database and admin passwords into Secrets; production points `database.host` at an external instance and sets `postgresql.enabled: false` ([Helm Chart](https://github.com/ferriskey/website/blob/2529ade8da32ac17b70c0c2e7e98f47de17b5fd1/apps/docs/src/content/docs/kubernetes/default/en/helm-chart.mdx)). Declaratively: install the operator chart, create a Secret with database credentials, apply a `FerrisKeyCluster` manifest ([Operator](https://github.com/ferriskey/website/blob/2529ade8da32ac17b70c0c2e7e98f47de17b5fd1/apps/docs/src/content/docs/kubernetes/default/en/operator.mdx)). Elsewhere: Docker Compose with profiles for registry images, local builds, or a single standalone container; or `cargo run` after `sqlx migrate run` ([Getting Started](https://github.com/ferriskey/website/blob/2529ade8da32ac17b70c0c2e7e98f47de17b5fd1/apps/docs/src/content/docs/discover/default/en/getting-started.mdx)). First start seeds the `master` realm, the admin user and the console client; everything after that is done in the console, the API, the CLI or Terraform.

**Testing and validating the installation.** `kubectl get pods` until the migration Job completes and the API and console pods are Running; the API exposes `/api/health/live` and `/api/health/ready`, used as the chart's probes; `kubectl get fkcl` prints readiness and phase for operator-managed clusters. Functionally: port-forward the console, sign in with the admin account, create a realm, register a client and request a token with `curl` against `/realms/{realm}/protocol/openid-connect/token`, as the getting started guide walks through. The chart ships a validation template that checks the exposure values (public host, Ingress or Gateway) at render time. Adopters are not expected to run the project's test suite.

### Security

#### Security self assessment

No cloud native security self assessment has been written yet. The maintainers plan to start it with TAG Security and Compliance after Sandbox acceptance, since the assessment is a joint exercise with the TAG. In the meantime the security policy is in [SECURITY.md](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/SECURITY.md) and the supply chain posture is tracked by the [OpenSSF Scorecard](https://scorecard.dev/viewer/?uri=github.com/ferriskey/ferriskey) and the [OpenSSF Best Practices badge](https://www.bestpractices.dev/projects/11019).

#### Cloud Native Security Tenets

**1. Security as a design requirement.** FerrisKey is an identity provider, so most of its behaviour is a security control. The main design evidence is the integration test suite under [`api/tests`](https://github.com/ferriskey/ferriskey/tree/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/api/tests), which runs in CI against PostgreSQL ([`rust.yaml`](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/.github/workflows/rust.yaml)). Named examples: a client that requires PKCE refuses an authorization without a challenge ([pkce_test.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/api/tests/pkce_test.rs#L453)); an authorization code is refused at another realm's token endpoint ([oidc_cross_realm_test.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/api/tests/oidc_cross_realm_test.rs#L576)); a code cannot be redeemed by another client ([oidc_conformance_test.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/api/tests/oidc_conformance_test.rs#L313)); a temporary MFA step token cannot be replayed to finish a login ([mfa_bypass_test.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/api/tests/mfa_bypass_test.rs#L396)); a caller missing a right in its own realm gets a 403 while a foreign realm answers 404, so that cross-realm probing learns nothing ([realm_cross_realm_test.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/api/tests/realm_cross_realm_test.rs#L823)). A source-level test freezes the list of files allowed to resolve a realm by hand, so that every other code path goes through the scoped resolver ([realm_scope_ratchet_test.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/api/tests/realm_scope_ratchet_test.rs)). The cross-realm test family was written after advisory [GHSA-v2hq-9v44-43ff](https://github.com/ferriskey/ferriskey/security/advisories/GHSA-v2hq-9v44-43ff) (critical, fixed in 0.8.0), which is the project's feedback loop so far. A threat model per flow is in review in [#1730](https://github.com/ferriskey/ferriskey/pull/1730); see Cloud Native Threat Modeling below.

**2. Secure configuration is the easiest path.** Clients created through the admin API require PKCE unless the caller opts out ([validators.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/libs/ferriskey-api-client/src/validators.rs#L44)); clients registered dynamically (RFC 7591) require PKCE whenever they are public ([client_registration/services.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/core/src/domain/client_registration/services.rs#L115)); the admin console itself is a public client with PKCE required. Realm defaults: password policy with a minimum length of 12 ([entity.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/libs/ferriskey-password-policy/src/entity.rs#L37)), account lockout after 10 failed attempts for 15 minutes ([realm/mod.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/libs/ferriskey-domain/src/realm/mod.rs#L289)), refresh token rotation, passwords hashed with Argon2id, session cookies HttpOnly and SameSite=Lax, with Secure set when the public URL is https ([auth.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/libs/ferriskey-api-authentication/src/handlers/auth.rs#L56)). The Helm chart generates a random admin password into a Secret on first install. The production guide is a checklist, not a tuning exercise ([Production Guide](https://github.com/ferriskey/website/blob/2529ade8da32ac17b70c0c2e7e98f47de17b5fd1/apps/docs/src/content/docs/kubernetes/default/en/production-guide.mdx)).

**3. Insecure configuration is a conscious decision.** The two switches that weaken network protections, `WEBHOOK_ALLOW_PRIVATE_ENDPOINTS` and `CLIENT_METADATA_ALLOW_PRIVATE_ENDPOINTS`, default to off and log a warning at startup that says never to enable them in production ([application/mod.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/core/src/application/mod.rs#L240)). `SERVER_TRUST_FORWARDED_FOR` defaults to off. Per client, PKCE and the resource owner password grant are explicit toggles. Known gap: the default `ADMIN_PASSWORD` is `admin` for a bare-metal or Compose install and nothing warns about it at startup; the seeded admin has no forced password change. The Helm path does not have this gap.

**4. Transition from insecure to secure state.** Legacy bcrypt password hashes are verified and rehashed to Argon2id at the next successful login, so imported user bases migrate without a reset ([rehash_password_if_needed](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/core/src/domain/authentication/services.rs#L4003)). Security changes ship as reversible SQL migrations with the rationale in the file, for example the admin console moving from a confidential client with an unusable secret to a public client with PKCE ([20260731000000](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/core/migrations/20260731000000_security_admin_console_public_pkce.up.sql)) and inbound PKCE on brokered logins ([20260819120000](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/core/migrations/20260819120000_broker_session_inbound_pkce.up.sql)). There are no feature gates; a secure default applies at upgrade and can be undone by the down migration.

**5. Secure defaults are inherited.** On Kubernetes the chart runs every container as non-root with a read-only root filesystem, all capabilities dropped, no privilege escalation and the RuntimeDefault seccomp profile ([values.yaml](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/charts/ferriskey/values.yaml#L262)). The API and operator images are built on `gcr.io/distroless/cc-debian12:nonroot`, the console on `nginx-unprivileged`. TLS is terminated by the Ingress or Gateway API HTTPRoute the chart renders, with cert-manager in the documented example, or natively by the API with rustls when `SERVER_TLS_CERT` and `SERVER_TLS_KEY` are set. The production guide asks for PostgreSQL TLS (`sslMode: require` or `verify-full`). What stays with the adopter is listed under "Security hardening" in the same guide: network policies, external secret management, image scanning, audit forwarding.

**6. Exception lists have first class support.** Redirect URIs match by exact string first; an operator may register an anchored pattern, and a URI that merely contains a registered value is refused ([redirect_uri_matching.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/libs/ferriskey-domain/src/client/redirect_uri_matching.rs)). Browser origins are allowed per client within a realm, and globally through `ALLOWED_ORIGINS` as exact origins with no wildcard. Maintenance mode carries a per-client allowlist of users who may still sign in. Token exchange is enabled per client under a policy object. Webhook destinations are resolved before connecting and loopback, private and link-local addresses are refused unless the switch above is on; link-local stays refused regardless ([delivery.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/core/src/infrastructure/webhook/delivery.rs#L228)). Security relevant events, including refused attempts, are recorded by the SeaWatch module.

**7. Protection against pervasive exploits.** Rust removes the memory safety class. Client secrets are compared in constant time ([client_secret_matches](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/core/src/domain/authentication/services.rs#L724)), secrets are wrapped in a masking type so they do not reach logs, webhook deliveries reject reserved headers and apply the SSRF guard above. The pipeline runs clippy with warnings as errors, `cargo deny` for advisories, bans, licenses and sources with every ignore justified in [deny.toml](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/deny.toml), a license check on the console, Dependabot weekly on Cargo, npm, GitHub Actions and Docker, and the OpenSSF Scorecard with SARIF upload. Known gaps: no static analysis or secret scanning job in CI, no image vulnerability scan in CI (a one-off Trivy report is in [docs/docker-hardening-report.md](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/docs/docker-hardening-report.md)), client secrets stored in clear in the database.

**8. Security limitations are explainable.** Documented today: the TLS at the proxy choice and the `ALLOWED_ORIGINS` semantics in the [Configuration guide](https://github.com/ferriskey/website/blob/2529ade8da32ac17b70c0c2e7e98f47de17b5fd1/apps/docs/src/content/docs/discover/default/en/guides/configuration.mdx), the adopter's share of hardening in the Production Guide, and the support window in SECURITY.md (security fixes land in the latest minor only while the project is pre-1.0). Not documented yet, and listed here on purpose: one RS256 2048-bit signing key per realm, generated once and stored in PostgreSQL, with no rotation path and no overlap of keys in the JWKS document; no HSM or KMS integration; the operator needs a cluster-wide role; no request rate limiting at the API layer beyond account lockout. A "Known limitations" page in the docs is planned.

#### Loosening the defaults

The adopter-facing knobs and their consequences are in the [Configuration guide](https://docs.ferriskey.rs/en/discover/guides/configuration) (versioned source linked above): `WEBHOOK_ALLOW_PRIVATE_ENDPOINTS` and `CLIENT_METADATA_ALLOW_PRIVATE_ENDPOINTS` for local development, `SERVER_TRUST_FORWARDED_FOR` behind a trusted proxy, unset `SERVER_TLS_*` to terminate TLS upstream. Per client, in the console or the API: `require_pkce`, `direct_access_grants_enabled`, `token_exchange_enabled`, `consent_required`. Per realm: password policy, lockout threshold and duration, `require_mfa`. The recommended production shape is the checklist at the end of the [Production Guide](https://docs.ferriskey.rs/en/kubernetes/production-guide).

#### Security Hygiene

**Frameworks, practices and procedures.** Vulnerability intake through GitHub private advisories or security@ferriskey.rs, with targets of 3 business days to acknowledge, 7 days to triage, 30 days to fix a critical or high issue and 90 days to disclose ([SECURITY.md](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/SECURITY.md)). One advisory published so far (GHSA-v2hq-9v44-43ff); a CVE was requested for it on 2026-10-17 and is pending assignment by GitHub. Every pull request needs a DCO sign-off and a review; `main` is protected. Dependencies are pinned through `Cargo.lock` and `pnpm-lock.yaml`, updated weekly by Dependabot, and gated by `cargo deny`. Security relevant behaviour is covered by integration tests that run on every push. Reviews so far are internal to the maintainers. Raw review reports stay private while any finding is open; the project publishes a summary with the scope and the fixed findings, linked to the advisories. No external audit or penetration test has been performed, and that is the first item the project would like to do with the TAG after acceptance.

**Features that are a security risk if left unmaintained.** The protocol implementations themselves: OpenID Connect and OAuth 2.0 (authorization code with PKCE, device flow, token exchange, back-channel logout, dynamic client registration), SAML 2.0, identity brokering to upstream providers, and the MFA module (TOTP, WebAuthn, magic links, recovery codes). Each carries a conformance or regression suite in `api/tests` so that a regression fails CI rather than a user. Password hashing and the JWT signing path live in a dedicated crate ([libs/ferriskey-security](https://github.com/ferriskey/ferriskey/tree/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/libs/ferriskey-security)) built on `argon2`, `jsonwebtoken` and `rustls`; the project does not implement cryptographic primitives. Pre-1.0, only the latest minor receives security fixes, which keeps the maintained surface small and is stated in SECURITY.md.

#### Cloud Native Threat Modeling

**Least privilege.** The API needs a PostgreSQL role on its own database and schema, outbound HTTPS to the identity providers it brokers to, to client metadata documents and to webhook endpoints, and SMTP if email is enabled. It binds a non-privileged port and runs as a non-root user with no capabilities. The operator, when used, needs a ClusterRole with read and write on Services, Secrets, Events, Deployments and Jobs, read on Pods and CustomResourceDefinitions, and status and finalizer updates on its own `FerrisKeyCluster` resource ([cluster-role.yaml](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/charts/ferriskey-operator/templates/operator/cluster-role.yaml)). Secrets are needed to store the generated admin and database passwords. A namespaced Role variant is not offered yet. A threat model lives next to this document in `docs/cncf/threat-model.md` ([#1730](https://github.com/ferriskey/ferriskey/pull/1730), in review). It lists, per flow, the threats and the mitigations in place, with the integration tests as evidence. Weaknesses that are not fixed yet are kept out of it on purpose and go through the private process in SECURITY.md.

**Certificate and key rotation.** Transport certificates are not managed by FerrisKey: on Kubernetes they come from the Ingress or Gateway and cert-manager, elsewhere from the proxy, or from the files passed to `SERVER_TLS_CERT` and `SERVER_TLS_KEY`, which are read at startup. Token signing keys are generated per realm on first use, RS256 with a 2048-bit RSA key, and persisted in PostgreSQL ([keystore_repository.rs](https://github.com/ferriskey/ferriskey/blob/fdf2056eff5b4377dbce7ff47e4efb87df7ef555/core/src/infrastructure/repositories/keystore_repository.rs#L94)). There is no rotation procedure yet, neither automatic nor through the API, and the JWKS document publishes a single key, so a compromise requires replacing the key and invalidating every outstanding token. This is the main open item in this section and is tracked for the roadmap. Client secrets and webhook secrets can be rotated through the API.

**Secure software supply chain.** Source: Apache-2.0, DCO on every commit, protected `main`, required review. Dependencies: lock files, weekly Dependabot, `cargo deny` with advisories, license allowlist and source restrictions, license policy on the console. Build: GitHub Actions with the actions in the test, supply chain and Scorecard workflows pinned by commit SHA; multi-architecture images built by digest and published to `ghcr.io/ferriskey`. Posture: OpenSSF Scorecard published, OpenSSF Best Practices badge. Known gaps against the CNCF supply chain paper at the pinned commit: images and release archives are not signed, no SBOM or provenance attestation is produced, and the Docker and release workflows pin actions by tag. Keyless cosign signing of the image digests, an SBOM and provenance attestation, a checksummed and signed source archive, and SHA pinning of the Docker and release workflows are in [#1728](https://github.com/ferriskey/ferriskey/pull/1728), opened 2026-10-17 and pending review.
